# iOS UDP 流媒体性能退化修复方案

- 编写日期：2026-10-31
- 分析基线：`e3925da`
- 范围：iOS Packet Tunnel、共享 Rust UDP 转发、VLESS/XUDP、Hysteria2
- 状态：分析与局部复现完成，生产修复尚未实施
- 目标场景：持续观看、连续切换视频、预加载和多 UDP 对端访问，例如 Bilibili 的部分播放场景

## 1. 结论与证据边界

当前实现存在使 UDP 密集流量在持续使用后卡顿、建立新连接变慢或反复重连的风险。主要原因是会话额度占用、清理任务滞留、内存保护覆盖不完整，以及突发流量下的队列丢包和调度开销。

不能据此认定运行时间本身必然导致性能下降，也不能认定所有 Bilibili 视频均使用 UDP。实际影响取决于播放协议、分流出口、连接创建速率、网络阻塞程度和设备内存。

| 发现 | 证据等级 | 适用范围 | 优先级 |
| --- | --- | --- | --- |
| UDP 会话或目标槽位耗尽后阻止新流量，关闭连接不立即释放目标槽位 | 已通过共享 Rust 路径复现 | iOS UDP，包括直连、代理和被接管的 DNS | P1 |
| XUDP END 清理任务在写入阻塞时继续持有底层流 | 已通过受控背压复现 | VLESS/XUDP，包括自动启用 XUDP 的 Vision | P1 |
| 内存保护未覆盖已有 UDP 目标上的新会话创建 | 代码确认，Apple 内存阈值未实测 | iOS 内存压力场景 | P1 |
| UDP 队列满时静默丢包 | 代码确认，真实播放损失率未实测 | 多会话、突发 UDP 流量 | P2 |
| 每包通知导致重复 drain 任务和临时缓冲分配 | 代码确认，真机调度影响未实测 | iOS 高包速率收包 | P2 |

本次验证运行于 Windows，使用 `internal_host_packet_io = true` 选择与 iOS 相同的连接预算。没有执行 iPhone 真机播放、Apple 内存阈值测试或 Instruments 性能采样。

## 2. 相关路径与当前限制

```text
NEPacketTunnelFlow
  → PacketTunnelProvider.submit
  → meta_write_packet_v1 / HostPackets
  → packet::run / udp_session
  → DIRECT UDP / VLESS XUDP / Hysteria2
  → Reply 队列 / smoltcp / HostPackets.send
  → packet_ready 回调
  → PacketTunnelProvider.drainPackets
  → NEPacketTunnelFlow.writePackets
```

| 项目 | 当前 iOS 路径限制或行为 |
| --- | --- |
| UDP 会话上限 | 256，按源端点和目标端点区分 |
| UDP 目标槽位上限 | 128，按目标 IP 与端口区分，并非仅数字端口 |
| 普通 UDP 会话输入空闲超时 | 60 秒 |
| 被接管的 DNS 会话输入空闲超时 | 15 秒 |
| UDP 目标槽位回收 | 最后一次收发后空闲超过 60 秒 |
| 每会话输入队列 | 16 包 |
| 共享 Reply 队列 | 256 包 |
| smoltcp 每个 UDP 目标的单方向存储 | 16 KiB 数据、16 个包元数据 |
| 内存保护阈值 | 40 MiB 开始限制新连接；45 MiB 取消被追踪的连接 |
| Swift 单次 drain | 最多读取 64 包，可继续排队执行 |

内存保护数值是项目当前策略，不代表所有 iOS 版本和设备都有固定的相同系统终止阈值。

## 3. 修复一：约束 XUDP 清理任务生命周期

### 3.1 问题与位置

- `crates/protocol/src/xudp.rs:308`：`MuxSession::drop` 为 END 帧创建独立后台任务。
- `crates/protocol/src/xudp.rs:324`：任务持有 `Arc<Shared>`。
- `crates/protocol/src/xudp.rs:328`：等待共享 writer，没有超时。
- `crates/protocol/src/xudp.rs:330`：写入和 flush，没有超时或退出取消。
- `crates/core/src/lib.rs:1350`：Vision 等配置会进入 XUDP 路径。

当 END 任务在其他会话存活时开始，并阻塞于底层写入，之后所有会话退出也不能保证释放底层流。多个关闭任务还可能排在同一 writer 后面。

复现已确认：所有会话与 multiplexer 所有者释放后，流仍被任务持有；对端继续消费 END 字节后，资源才释放。实际网络中的滞留时间取决于传输何时完成或报错。

### 3.2 实施要求

1. 为 multiplexer 增加明确的退出信号，最后一个所有者退出时取消关联清理工作。
2. 对 END 的等待写锁、写入和 flush 设置覆盖完整操作的期限，不能只限制最后一次写调用。
3. 优先将清理请求交给受 multiplexer 管理的有界 writer 队列，避免每个 Drop 都创建无界独立任务。也可先实施带超时和取消的最小修复，但仍需限制待清理任务数。
4. 明确队列饱和策略，不能为了发送 END 而无限保留资源。
5. 一旦帧已部分写入后被取消或超时，必须将整个共享流标记不可用，唤醒关联会话并触发重建，防止后续帧错位。
6. 对“尚未取得 writer”与“已经开始写帧”分别处理；不要把未写入任何字节的取消误报为帧损坏。

超时时间应由弱网测试确定，不能将测试用的毫秒级时间直接作为生产配置。

### 3.3 验收标准

- 对端停止读取时，关闭会话不会使清理任务数随关闭次数无限增长。
- multiplexer 退出后，所有关联清理任务和底层流在测试约定期限内释放。
- 取消部分写入后，不继续复用损坏的共享流；关联会话能收到错误并重新建立。
- 健康连接上的单会话关闭不影响其他会话。

## 4. 修复二：统一 UDP 准入与目标槽位回收

### 4.1 问题与位置

- `crates/core/src/packet.rs:76`：iOS 使用 256 会话、128 目标槽位预算。
- `crates/core/src/packet.rs:762`：目标槽位满时不创建新 socket；smoltcp 可返回 ICMP 不可达。
- `crates/core/src/packet.rs:890`：会话额度满时没有明确拒绝反馈，数据被静默丢弃。
- `crates/core/src/packet.rs:914`：目标槽位按空闲时间回收，不随最后一个会话结束立即回收。

已复现：第 129 个目标无法转发，旧目标仍正常；第 257 个源端口会话被静默丢弃。取消全部被追踪的连接后，目标槽位仍保留。

这不是天然的无限泄漏：无新流量且超过空闲期限后应当回收。但持续切换目标可能让滚动窗口内的占用长期接近上限。

### 4.2 实施要求

1. 建立统一的 UDP 准入判断，区分已有会话、新会话、新目标、内存保护和各类容量限制。
2. 为目标槽位维护活动会话关联；会话结束时更新关联，不能仅依赖目标最后活动时间。
3. 新目标准入前优先回收超时、无活动会话且没有待交付回包的槽位。不要直接淘汰仍活跃的视频会话。
4. 关闭全部连接时协调会话、目标 socket 和待交付队列的回收；避免统计连接数归零而大部分数据面资源仍然占用。
5. 防止复用后的旧任务完成事件或旧 Reply 误命中新会话。必要时增加会话代次标识，清理和回包必须校验归属。
6. 到达会话上限时记录原因并采用明确、受限速保护的拒绝反馈，避免长时间黑洞。沿用现有拒绝缓存与 ICMP 逻辑前，需核对客户端回退行为。
7. 评估为 DNS 预留小额会话预算或使用独立额度，避免数据流量耗尽会话后连域名解析也被阻塞；需同时防止 DNS 滥用。

不以单纯提高 256/128 上限作为修复。提高上限可能提前触发内存保护或系统终止。

### 4.3 验收标准

- 达到容量限制时，旧的健康会话保持可用；新会话有可观测、可解释的处理结果。
- 存在可回收槽位时，新目标无需等待完整 60 秒才能接入。
- 关闭全部连接后，任务、关联表和不再需要的目标槽位能收敛。
- 大量源端口和目标端点反复复用时，没有旧回包串流、错误取消新会话或遗漏回收。
- DNS 在数据会话接近上限时仍能正常服务。

## 5. 修复三：补齐内存保护并避免重建循环

### 5.1 问题与位置

`crates/core/src/packet.rs:762` 的新目标创建检查了 `!guard.shedding`，但 `:890` 的新 UDP 会话创建没有检查。内存压力下，向已有目标创建新源端口会话仍会分配队列、任务与出口资源。

`crates/core/src/packet.rs:171` 取消被追踪的连接后，未立即回收的目标槽位又给新会话提供了创建条件，存在取消、重建、再次取消的风险。

### 5.2 实施要求

1. 所有新 UDP 会话创建路径均检查内存准入状态，覆盖已有目标上的新源端口。
2. 保护期间继续服务健康的已有会话，限制新资源分配；恢复条件应明确，并评估迟滞或冷却期，避免阈值附近抖动。
3. 紧急回收要覆盖正在建连但尚未登记 Tracker 的会话任务，以及无会话的目标槽位；不能只以连接列表作为全部资源清单。
4. 将内存采样与决策分离，使用可注入的内存读数测试准入、恢复和紧急回收逻辑，避免测试依赖真实设备达到危险内存值。
5. 保留低频汇总日志，记录进入保护、恢复和紧急回收各发生多少次、实际释放多少资源。

### 5.3 验收标准

- 注入保护状态后，无论目标是否已存在，都不再创建新的普通 UDP 会话。
- 恢复后可以重新准入，既有会话和 DNS 的处理遵守明确策略。
- 连续制造内存压力时，资源数能下降，不持续出现立即重建导致的回收循环。
- Apple 真机上内存、任务数、文件描述符与播放情况相互对应，不能仅凭“VPN 没断”判断修复有效。

## 6. 修复四：补充丢包观测与合并 iOS 包通知

### 6.1 队列观测

当前需要分别统计以下丢包或拒绝，不能只给出一个总数：

- UDP 会话准入失败、目标槽位准入失败、内存保护拒绝。
- 每会话输入队列满：`crates/core/src/packet.rs:900`。
- 共享 Reply 队列满：`crates/core/src/packet.rs:601`。
- smoltcp 回包发送队列满或数据超限：`crates/core/src/packet.rs:910`。
- XUDP/Hysteria2 内部接收队列满。

使用累计计数和低频速率汇总，避免每丢一包就打印日志。队列长度和数据字节数应同时统计；增加队列容量前先核算最坏内存占用。

### 6.2 iOS 通知合并

- `crates/ffi/src/host.rs:109`：当前每包通知宿主。
- `ios/Tunnel/PacketTunnelProvider.swift:59`：每次通知向串行队列追加 drain。
- `ios/Tunnel/PacketTunnelProvider.swift:228`：每次 drain 分配 65,535 字节临时缓冲。
- `ios/Tunnel/PacketTunnelProvider.swift:257`：drain 还会自行追加后续任务。

实施时应满足：

1. 用线程安全的调度状态合并通知，同一时刻只保留有界数量的待执行或正在执行 drain 工作。
2. 不能只在串行队列内部设置标记，因为回调可能已经排入大量待执行闭包。
3. 清除“已调度”状态与检查队列为空之间必须有正确的握手，避免最后一个包到达时丢失唤醒。
4. 保留每次处理包数或时间片上限，避免 drain 独占串行队列，影响上行包、网络变化与健康检查。
5. 在串行队列内复用 scratch 缓冲，确认 `writePackets` 使用的数据具有独立、正确的生命周期。
6. shutdown/restart 用 epoch 或等价机制隔离旧通知，禁止旧 drain 操作新 core。

### 6.3 验收标准

- 突发通知不会产生与总包数同等规模的排队任务。
- 队列从非空到空及重新到达的竞争测试中，无丢失唤醒、重复交付或永久停收。
- 运行中停止、重启隧道不会触发旧回调访问新实例。
- 真机同等负载下比较 CPU、内存峰值、队列延迟与吞吐；不预先宣称固定百分比收益。

## 7. 第二阶段性能优化

完成上述生命周期和准入修复后，再依据计数器和 Instruments 结果决定是否实施：

- 复用 DIRECT UDP 的接收 scratch，减少 `crates/core/src/lib.rs:1730` 的每包 64 KiB 临时分配。现有返回数据已按实际长度复制，不能重新引入大容量 Vec 长期滞留的问题。
- 根据实测突发大小调整队列，同时限定累计字节数，避免小包容量与大包内存失配。
- 优化 packet loop 的全表扫描和 2 ms tick 唤醒，保持 TCP 定时器、重传、空闲回收和任务完成处理的正确性。
- 检查 VLESS/XUDP 多会话共享可靠字节流造成的队头阻塞。它属于传输特性，不能仅靠扩大 UDP 队列解决。

### 8.3 iOS 真机长时间验证

使用 Release Rust XCFramework；仅切换 Xcode 为 Release 不会重新编译 Rust 内核。

```bash
bash scripts/build-ios.sh --release
```

固定设备、网络、视频集合和清晰度，在基线版与修复版各执行 30～60 分钟测试。至少覆盖连续播放、频繁切视频、直播、弱网与 Wi-Fi/蜂窝切换，记录实际使用的传输协议。

| 对照路径 | 目的 |
| --- | --- |
| DIRECT UDP | 判断共享 TUN/Swift/UDP 准入问题 |
| VLESS/XUDP | 验证关闭任务修复与共享流背压行为 |
| Hysteria2 | 区分 XUDP 特有问题和共享数据面问题 |
| 仅针对测试流量拒绝 UDP/443，观察 TCP 回退 | 协议对照；不作为全局禁用 UDP 的修复方案 |

每次记录：播放缓冲时间、切换首帧耗时、实际吞吐、UDP 会话数、目标槽位数、各级队列丢包率、待清理任务数、内存、CPU、文件描述符和重连次数。温度或系统热状态作为解释性能变化的辅助信息。

现有可用日志关键字：

```text
memory load
memory high; refusing new connections
memory critical; closed all connections
running: memory=... connections=... files=...
core packet input full for 5 s
tunnel queue blocked
```

验收不能要求网络永不丢包。需要证明在相同负载下，内部资源不会无界增长；压力解除后能恢复；没有因内部准入黑洞或清理任务滞留造成持续恶化。吞吐和缓冲收益以基线对照结果报告。
